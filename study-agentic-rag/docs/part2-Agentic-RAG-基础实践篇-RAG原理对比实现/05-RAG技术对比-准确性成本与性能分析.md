## 三、评估指标体系

### 指标1：准确性（Accuracy）

**如何评估？**

由于RAG答案是生成式的，不能简单用"对/错"判断。我们采用**5分制人工评分**：

| 分数 | 标准 | 说明 |
|------|------|------|
| 5分 | 完全准确 | 信息完整、准确、逻辑清晰 |
| 4分 | 基本准确 | 主要信息正确，有小瑕疵 |
| 3分 | 部分准确 | 部分信息正确，遗漏关键点 |
| 2分 | 大部分错误 | 信息严重不足或有误 |
| 1分 | 完全错误 | 答非所问或严重幻觉 |

**自动化评估（可选）**
```python
def evaluate_answer_with_llm(question, answer, reference):
    """使用LLM作为评判者（LLM-as-Judge）"""
    prompt = f"""
    问题: {question}
    生成答案: {answer}
    参考答案: {reference}

    请从1-5分评估生成答案的质量（5分最高）：
    - 完整性：是否覆盖所有要点
    - 准确性：是否有事实错误
    - 相关性：是否紧扣问题

    只返回分数（1-5）。
    """
    # 调用LLM获取评分
    score = llm_call(prompt)
    return int(score)
```

### 指标2：成本（Cost）

**计算公式：**

```
总成本 = LLM调用次数 × 单次调用成本
```

**各系统的LLM调用模式：**

| 系统 | LLM调用场景 | 平均次数/查询 |
|------|------------|--------------|
| 传统RAG | 1. 嵌入查询<br>2. 生成答案 | 2次 |
| Agentic RAG | 1. 嵌入查询<br>2. 思考决策<br>3. 评估质量<br>4. 生成答案<br>5. 可能的多次迭代 | 5-8次 |

**成本参考（阿里云百炼平台）：**
- Qwen-Plus：¥0.004/1K tokens（输入）、¥0.012/1K tokens（输出）
- 平均每次调用约500 tokens，估算单次成本 ≈ ¥0.005

### 指标3：性能（Performance）

**测量维度：**

1. **响应时间（Latency）**
   - 从用户提问到返回答案的总时间
   - 包括检索、推理、生成所有阶段

2. **吞吐量（Throughput）**
   - 每秒能处理的查询数（QPS）
   - 衡量系统并发能力

**性能测试代码框架：**

```python
import time

def benchmark_rag_system(rag_system, questions):
    """性能测试"""
    latencies = []

    for question in questions:
        start_time = time.time()
        answer = rag_system.query(question)
        end_time = time.time()

        latency = end_time - start_time
        latencies.append(latency)

    return {
        "avg_latency": sum(latencies) / len(latencies),
        "min_latency": min(latencies),
        "max_latency": max(latencies),
        "p95_latency": sorted(latencies)[int(len(latencies) * 0.95)],
        "throughput": 1.0 / (sum(latencies) / len(latencies))  # QPS
    }
```

## 四、对比实验结果

### 实验1：准确性对比

**测试配置：**
- 文档集：100篇AI技术文档
- 测试集：30个问题（简单/中等/复杂各10个）
- 评估：5分制人工打分

**结果数据：**

| 查询类型 | 传统RAG平均分 | Agentic RAG平均分 | 提升幅度 |
|---------|--------------|------------------|---------|
| 简单查询 | 4.2 | 4.5 | +7% |
| 中等查询 | 3.5 | 4.3 | +23% |
| 复杂查询 | 2.1 | 4.0 | +90% |
| **整体平均** | **3.27** | **4.27** | **+31%** |

**可视化图表：**

```
准确性对比（满分5分）

简单查询:  ████████▌ 4.2          ████████▊ 4.5
          传统RAG                Agentic RAG

中等查询:  ███████░░ 3.5          ████████▌ 4.3
          传统RAG                Agentic RAG

复杂查询:  ████░░░░░ 2.1          ████████░ 4.0
          传统RAG                Agentic RAG
```

**关键发现：**

1. **简单查询差距小（+7%）**
   - 传统RAG的"检索-生成"流程已经足够
   - Agentic RAG的优势不明显
   - 额外成本不值得

2. **中等查询有明显提升（+23%）**
   - 需要整合多个信息片段
   - Agentic RAG的迭代检索发挥作用
   - 质量评估避免低质量片段

3. **复杂查询提升巨大（+90%）**
   - 需要多步推理或工具调用
   - 传统RAG几乎无法处理
   - Agentic RAG的智能决策至关重要

### 实验2：成本对比

**测试配置：**
- 场景：每天10000次查询
- 时间周期：30天（1个月）
- LLM定价：参考阿里云百炼平台

**结果数据：**

| 指标 | 传统RAG | Agentic RAG | 差异 |
|------|---------|-------------|------|
| 单次查询LLM调用 | 2次 | 6次（平均） | +200% |
| 单次查询成本 | ¥0.010 | ¥0.030 | +200% |
| 日成本 | ¥100 | ¥300 | +200% |
| **月成本** | **¥3,000** | **¥9,000** | **+200%** |

**成本分解（Agentic RAG）：**

```
Agentic RAG 单次查询成本分解：

嵌入查询：      ¥0.002  (6.7%)
思考决策：      ¥0.008  (26.7%)
工具调用：      ¥0.005  (16.7%)
评估质量：      ¥0.007  (23.3%)
生成答案：      ¥0.008  (26.7%)
─────────────────────────────
总计：         ¥0.030  (100%)
```

**关键发现：**

1. **成本主要在推理环节**
   - Think（思考）和Observe（评估）占比50%
   - 这是Agentic RAG的核心能力所在
   - 优化方向：减少不必要的评估

2. **迭代次数影响巨大**
   - 平均迭代2次：成本 ¥0.030
   - 平均迭代3次：成本 ¥0.042（+40%）
   - 设置合理的max_iterations很重要

3. **成本控制策略**
   - 简单查询用传统RAG（占70%）
   - 复杂查询用Agentic RAG（占30%）
   - 混合策略可节省成本56%

**测试配置：**
- 硬件：8核CPU，16GB内存

## 五、技术选型决策树

```
     │             │
```

**详细决策规则：**

### 场景1：选择传统RAG

**适用条件（满足任意1条）：**
- ✅ 查询以简单问题为主（占70%以上）
- ✅ 成本预算紧张（预算<¥5,000/月）
- ✅ 对响应时间要求高（<2秒）
- ✅ 高并发场景（QPS>10）
- ✅ 团队技术能力有限

**典型应用场景：**
- 企业内部知识库问答
- 产品FAQ系统
- 简单客服机器人
- 文档检索系统

**优势：**
- 成本低（仅传统方案的1/3）
- 响应快（1-2秒）
- 实现简单（200行代码）
- 稳定可靠

**劣势：**
- 无法处理复杂查询
- 信息整合能力弱
- 缺乏推理能力

### 场景2：选择Agentic RAG

**适用条件（满足任意2条）：**
- ✅ 查询复杂度高（需要多步推理）
- ✅ 需要多数据源整合（知识库+实时信息）
- ✅ 准确性要求高（关键业务场景）
- ✅ 响应时间容忍度高（可接受5-10秒）
- ✅ 成本不敏感

**典型应用场景：**
- 智能研究助手
- 复杂业务咨询系统
- 金融分析工具
- 医疗诊断辅助
- 法律文书分析

**优势：**
- 准确率高（提升31%）
- 处理复杂查询（提升90%）
- 多工具协作
- 智能决策

**劣势：**
- 成本高（传统方案的3倍）
- 响应慢（8-12秒）
- 实现复杂（600行代码）
- 调试困难

### 场景3：混合方案（推荐）

**核心思想：**
根据查询复杂度动态路由，简单查询用传统RAG，复杂查询用Agentic RAG。

**架构图：**

```
        用户查询
           ↓
    ┌─────────────┐
    │ 智能路由器   │ ← 判断复杂度
    └──────┬──────┘
           │
    ┌──────┴──────┐
    │             │
  简单(70%)    复杂(30%)
    │             │
    ▼             ▼
┌────────┐   ┌────────┐
│传统RAG │   │Agentic │
│  引擎  │   │RAG引擎 │
└───┬────┘   └───┬────┘
    │            │
    └─────┬──────┘
          ↓
       返回答案
```

**成本优化效果：**

```python
# 纯传统RAG（准确性不足）
```

**混合方案的价值：**
- 成本节省 **47%**
- 准确性仅降低 **16%**
- 响应时间显著改善（70%查询<2秒）
- **性价比最优**

**路由器设计（简单版）：**

```python
def classify_query_complexity(query: str) -> str:
    """判断查询复杂度"""

    # 规则1：关键词判断
    complex_keywords = ["对比", "分析", "计算", "为什么", "如何", "设计", "评估"]
    simple_keywords = ["什么是", "定义", "是什么"]

    if any(kw in query for kw in complex_keywords):
        return "complex"
    elif any(kw in query for kw in simple_keywords):
        return "simple"
    else:
        return "medium"  # 默认中等

    # 规则2：字数判断
    if len(query) > 50:
        return "complex"
    elif len(query) < 15:
        return "simple"

    # 规则3：LLM深度判断（可选）
    # prompt = f"判断查询复杂度：{query}\n返回：simple/medium/complex"
    # return llm_call(prompt)

def route_to_engine(query: str):
    """路由到合适的引擎"""
    complexity = classify_query_complexity(query)

    if complexity in ["simple", "medium"]:
        return traditional_rag.query(query)
    else:
        return agentic_rag.query(query)
```

## 六、实战建议

### 1. 初创团队

**推荐：传统RAG + 逐步优化**

```
阶段1（第1-2个月）：
└─ 实现传统RAG MVP
   └─ 验证业务可行性
   └─ 积累用户反馈

阶段2（第3-4个月）：
└─ 分析常见复杂查询
   └─ 针对性优化Prompt
   └─ 改进分块策略

阶段3（第5-6个月）：
└─ 对复杂查询引入Agentic RAG
   └─ 实现混合路由系统
   └─ 持续优化准确率
```

**理由：**
- 快速上线，验证市场
- 降低初期成本
- 逐步提升能力

### 2. 成熟企业

**推荐：混合方案**

```
架构设计：
├─ 智能路由层（分流查询）
├─ 传统RAG引擎（高吞吐）
├─ Agentic RAG引擎（高质量）
├─ 监控告警（性能追踪）
└─ A/B测试（持续优化）
```

**理由：**
- 平衡成本和质量
- 支持大规模并发
- 数据驱动优化

### 3. 研究机构/高端场景

**推荐：纯Agentic RAG**

```
优化方向：
├─ 模型微调（提升准确率）
├─ 工具扩展（增加能力）
├─ 缓存策略（降低成本）
└─ 并行推理（提升速度）
```

**理由：**
- 准确性第一优先级
- 成本相对不敏感
- 需要复杂推理能力

| **适用场景** | 简单查询 | 复杂查询 | 通用场景 |
| **推荐指数** | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

### 三个关键认知

1. **没有银弹**
   - 不存在"完美的RAG技术"
   - 选择取决于业务场景和约束条件
   - 混合方案通常是最优解

2. **成本与质量的权衡**
   - Agentic RAG质量提升31%，但成本增加200%
   - 需要根据ROI做决策
   - 不是所有查询都需要最高质量

3. **循序渐进**
   - 从简单开始，逐步演进
   - 用数据驱动优化
   - 避免过度设计
