## 一、LLM 的能力与局限：为什么需要 RAG？

### 1.1 大语言模型的强大能力

大语言模型（LLM）在过去几年取得了惊人的突破。它们可以：

- **理解自然语言**：像人一样理解复杂的问题
- **生成流畅文本**：写作、翻译、总结等
- **推理和分析**：解决数学题、编写代码
- **对话交互**：进行多轮对话

### 1.2 但 LLM 有三个致命问题

尽管强大，LLM 仍然面临三个核心挑战：

**问题1：知识截止日期**

```
用户：2024年诺贝尔物理学奖得主是谁？
LLM：抱歉，我的训练数据截止到2023年4月，无法回答这个问题。
```

LLM 的知识冻结在训练时刻，无法获取最新信息。

**问题2：幻觉问题（Hallucination）**

```
用户：我们公司2024年第三季度的销售额是多少？
LLM：根据我的了解，你们公司第三季度销售额约为500万美元。
      （注意：这是编造的！LLM从未见过你的公司数据）
```

LLM 在不知道答案时，可能会"自信地"编造内容。

**问题3：无法访问私有数据**

```
用户：帮我总结一下上周的会议纪要。
LLM：抱歉，我无法访问您的私有文档和数据。
```

LLM 无法访问企业内部文档、个人文件等私有数据。

### 1.3 解决方案：RAG（检索增强生成）

RAG 的核心思想很简单：

```
在让 LLM 回答问题之前，先去相关的知识库里"查资料"，
然后把查到的资料和问题一起给 LLM，让它基于真实资料来回答。
```

就像学生考试时可以"开卷"，LLM 通过 RAG 也可以"查资料"再回答。

## 二、传统 RAG：一次性检索的简单方案

### 2.1 传统 RAG 的工作流程

传统 RAG 的流程非常直接，就像流水线一样：

```
┌─────────────┐
│  用户提问   │  "孙悟空是谁？"
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  向量化查询 │  将问题转换为数字向量
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  相似度搜索 │  在向量数据库中找到最相关的文档
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  拼接上下文 │  将查到的文档和问题组合起来
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  LLM 生成   │  基于上下文生成答案
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  返回答案   │  "孙悟空是《西游记》中的主角，原本是花果山上..."
└─────────────┘
```

### 2.2 核心步骤详解

**步骤1：向量化（Embedding）**

将文本转换为数字向量（一串数字），相似的文本会有相似的向量。

```
"孙悟空是谁？"  →  [0.12, 0.85, -0.34, ..., 0.56]  (1536维向量)
```

**步骤2：相似度搜索**

在向量数据库中，找到与查询向量最相似的文档向量。

```
数据库中的文档：
文档1："孙悟空原本是花果山上的一块仙石..."  (相似度: 0.92) ✓
文档2："唐僧是《西游记》的主角之一..."      (相似度: 0.75)
文档3："猪八戒原本是天蓬元帅..."            (相似度: 0.68)

选择相似度最高的 Top-3 文档
```

**步骤3：上下文拼接**

把查到的文档和用户问题组合成一个完整的提示词（Prompt）：

```
Prompt:
```
上下文信息：
文档1: 孙悟空原本是花果山上的一块仙石孕育而生的石猴...
文档2: 唐僧是《西游记》的主角之一...
文档3: 猪八戒原本是天蓬元帅...

问题: 孙悟空是谁？

请基于以上上下文回答问题。
```
```

**步骤4：LLM 生成答案**

LLM 基于提供的上下文生成答案，而不是凭空编造。

### 2.3 传统 RAG 的特点

**优势：**
- ✅ **简单直接**：流程清晰，易于实现
- ✅ **响应快速**：通常 1-2 秒就能返回答案
- ✅ **成本低**：只调用一次 LLM
- ✅ **可预测**：相同问题得到相同结果

**局限：**
- ❌ **单一数据源**：只能从一个向量数据库检索
- ❌ **一次性检索**：无法根据结果质量调整策略
- ❌ **无法验证**：不知道检索到的内容是否真正相关
- ❌ **处理不了复杂查询**：需要多步推理的问题效果差

## 三、Agentic RAG：智能体驱动的升级方案

### 3.1 什么是 Agentic RAG？

**Agentic RAG = RAG + AI Agent（智能体）**

```
传统 RAG：   机械的流水线（固定步骤）
Agentic RAG： 有"大脑"的智能助手（自主决策）
```

**智能体（Agent）** 是一个能够：
- **思考（Think）**：分析问题，制定计划
- **行动（Act）**：调用工具获取信息
- **观察（Observe）**：评估结果，调整策略
- **循环迭代**：不满意就重新尝试

### 3.2 Agentic RAG 的工作流程

Agentic RAG 采用 **ReAct 框架**（Reasoning + Acting），流程更加智能和灵活：

```
┌─────────────┐
│  用户提问   │  "孙悟空和猪八戒有什么区别？"
└──────┬──────┘
       │
       ▼
┌─────────────────────────────┐
│ Thought（思考）              │
│  - 这个问题需要两个角色的信息│
│  - 需要先了解孙悟空，再了解猪八戒 │
│  - 然后进行对比分析          │
└──────┬──────────────────────┘
       │
       ▼
┌─────────────────────────────┐
│ Action（行动）               │
│  决策: 使用向量搜索工具      │
│  参数: query="孙悟空的背景和特点" │
└──────┬──────────────────────┘
       │
       ▼
┌─────────────────────────────┐
│ Observation（观察）          │
│  结果: "孙悟空是石猴，会七十二变..." │
│  评估: 信息充分，质量好 ✓    │
└──────┬──────────────────────┘
       │
       ▼
┌─────────────────────────────┐
│ Thought（再次思考）          │
│  - 孙悟空的信息已获取        │
│  - 现在需要猪八戒的信息      │
└──────┬──────────────────────┘
       │
       ▼
┌─────────────────────────────┐
│ Action（再次行动）           │
│  决策: 再次使用向量搜索      │
│  参数: query="猪八戒的背景和特点" │
└──────┬──────────────────────┘
       │
       ▼
┌─────────────────────────────┐
│ Observation（再次观察）      │
│  结果: "猪八戒原本是天蓬元帅..." │
│  评估: 信息充分 ✓            │
└──────┬──────────────────────┘
       │
       ▼
┌─────────────────────────────┐
│ Thought（最终思考）          │
│  - 两个角色的信息都已收集完整 │
│  - 可以进行对比分析了        │
│  - 生成最终答案              │
└──────┬──────────────────────┘
       │
       ▼
┌─────────────┐
│  返回答案   │  "孙悟空和猪八戒的主要区别在于..."
└─────────────┘
```

### 3.3 Agentic RAG 的核心创新

**创新1：多工具访问**

传统 RAG 只能访问向量数据库，Agentic RAG 可以使用多种工具：

```
工具箱：
├── 向量搜索工具  （从知识库检索）
├── Web搜索工具   （获取最新信息）
├── 计算器工具     （进行数学计算）
├── API调用工具    （访问外部服务）
└── 自定义工具     （可扩展）
```

**创新2：智能决策**

Agent 可以根据问题类型，自主选择合适的工具：

```
问题：公司休假政策是什么？
Agent思考：这是内部文档问题 → 使用向量搜索

问题：今天北京天气如何？
Agent思考：这需要实时信息 → 使用Web搜索

问题：如果每月工资1万，年薪是多少？
Agent思考：这是计算问题 → 使用计算器工具
```

**创新3：迭代检索与质量验证**

Agentic RAG 可以评估检索结果，不满意就重新检索：

```
第1次检索：query="西游记"
观察：结果太宽泛，不够具体
↓
第2次检索：query="西游记主要人物"
观察：更接近了，但还需要细节
↓
第3次检索：query="西游记孙悟空的性格特点"
观察：很好！得到了需要的信息 ✓
```

**创新4：复杂查询处理**

Agentic RAG 可以将复杂问题分解为多个子问题：

```
复杂问题："过去一周我们产品的市场反馈如何？主要竞争对手有什么新动向？"

Agent的思考过程：
1. 这个问题包含两个部分
2. 第一部分：我们产品的市场反馈
   → 需要查询内部CRM数据（使用内部API）
3. 第二部分：竞争对手动向
   → 需要查询最新新闻（使用Web搜索）
4. 最后：整合两部分信息，生成综合答案
```

## 四、传统 RAG vs Agentic RAG：核心区别对比

### 4.1 对比表

| 对比维度 | 传统 RAG | Agentic RAG |
|---------|---------|-------------|
| **工作模式** | 固定流水线 | 智能决策循环 |
| **数据源** | 单一向量库 | 多源（向量库+Web+API） |
| **检索次数** | 固定1次 | 动态多次，按需调整 |
| **决策能力** | 无，完全被动 | 有，主动规划 |
| **结果验证** | 无 | 有，评估并迭代 |
| **工具数量** | 1个（向量搜索） | 多个（可扩展） |
| **响应时间** | 快（1-2秒） | 较慢（5-15秒） |
| **准确率** | 70-80% | 85-95% |
| **成本** | 低（1次LLM调用） | 高（3-5次LLM调用） |
| **适用场景** | 简单查询 | 复杂查询 |

### 4.2 具体案例对比

**案例1：简单事实查询**

```
问题：孙悟空是谁？

传统 RAG：
1. 向量搜索 → 找到答案 → 生成回复  ✓
时间：1.5秒
调用：1次LLM

Agentic RAG：
1. 思考：这是简单查询
2. 行动：向量搜索
3. 观察：结果充分
4. 生成回复 ✓
时间：3秒
调用：2次LLM

结论：简单查询用传统RAG更高效
```

**案例2：多步推理查询**

```
问题：孙悟空和猪八戒谁更厉害？请从武力、智慧、性格三个方面分析。

传统 RAG：
1. 向量搜索"孙悟空猪八戒比较" → 可能找不到直接对比的文档
2. 基于有限信息生成答案
结果：答案可能片面或不完整 ✗
时间：2秒
准确性：60%

Agentic RAG：
1. 思考：需要分别了解两个角色，然后对比
2. 行动1：搜索"孙悟空武力智慧性格"
3. 观察1：得到孙悟空的详细信息 ✓
4. 行动2：搜索"猪八戒武力智慧性格"
5. 观察2：得到猪八戒的详细信息 ✓
6. 思考：信息充分，可以进行多维度对比了
7. 生成综合答案
结果：全面的多维度分析 ✓
时间：8秒
准确性：90%

结论：复杂查询用Agentic RAG效果更好
```

**案例3：需要实时信息**

```
问题：今天北京的天气如何？

传统 RAG：
1. 向量搜索 → 找不到实时天气信息
2. 回复"抱歉，我没有实时天气信息" ✗

Agentic RAG：
1. 思考：这需要实时信息，向量库里没有
2. 决策：使用Web搜索工具
3. 行动：调用Web搜索"北京今天天气"
4. 观察：获取到最新天气信息 ✓
5. 生成答案："今天北京晴天，温度15-25度..."

结论：Agentic RAG可以获取实时信息
```

## 五、适用场景：如何选择？

### 5.1 选择决策树

```
开始
│
├─ 需要实时Web信息？
│  └─ 是 → 使用 Agentic RAG
│
├─ 需要多个数据源？
│  └─ 是 → 使用 Agentic RAG
│
├─ 需要复杂推理（多步骤）？
│  └─ 是 → 使用 Agentic RAG
│
├─ 需要快速响应（<2秒）？
│  └─ 是 → 使用 Traditional RAG
│
├─ 成本敏感（预算有限）？
│  └─ 是 → 使用 Traditional RAG
│
└─ 简单事实查询？
   └─ 是 → 使用 Traditional RAG
```

### 5.2 传统 RAG 适用场景

**推荐使用场景：**

1. **企业内部文档查询**
   - 查询公司政策、流程手册
   - 快速FAQ系统
   - 产品使用说明

2. **客服机器人（简单问题）**
   - "如何重置密码？"
   - "退货政策是什么？"
   - "营业时间是几点？"

3. **高并发场景**
   - 需要服务大量用户
   - 对响应时间要求严格
   - 成本需要控制

### 5.3 Agentic RAG 适用场景

**推荐使用场景：**

1. **智能研究助手**
   - 需要查询多个信息源
   - 需要综合分析
   - 需要最新的网络信息

2. **复杂业务分析**
   - "过去一个月市场趋势如何？"
   - "竞品分析报告"
   - "基于数据给出业务建议"

3. **个人智能助理**
   - 整合邮件、日程、任务
   - 需要访问多个API
   - 需要智能决策和推荐

4. **技术支持系统**
   - 需要多步骤故障排查
   - 需要查询文档、日志、监控数据
   - 需要综合分析给出解决方案

### 5.4 混合方案：最佳实践

实际应用中，最好的方案是**智能路由**：

```
用户查询
↓
[智能路由器]
├─ 简单查询 → Traditional RAG（快速、便宜）
└─ 复杂查询 → Agentic RAG（准确、智能）
```

这样可以：
- **节省成本**：70%的简单查询用传统RAG处理
- **保证质量**：30%的复杂查询用Agentic RAG保证准确性
- **综合效果**：成本降低50%+，准确率提升30%+

## 本讲总结

**核心要点：**

1. **LLM的局限性**：知识截止、幻觉问题、无法访问私有数据
2. **传统RAG**：简单高效的"检索+生成"流水线
3. **Agentic RAG**：引入智能体的"思考+行动+观察"循环
4. **关键区别**：Agentic RAG多源、多次、可验证、智能决策
5. **选择原则**：简单查询用传统RAG，复杂任务用Agentic RAG

**技术本质：**

```
传统 RAG    = 流水线工人（机械重复）
Agentic RAG = 专业顾问（分析决策）
```
