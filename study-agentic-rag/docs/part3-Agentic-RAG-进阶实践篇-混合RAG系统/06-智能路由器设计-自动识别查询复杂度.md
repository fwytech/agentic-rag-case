# 第6讲：智能路由器设计 - 自动识别查询复杂度

在第5讲中，我们得出了一个重要结论：**混合方案是最优解**——简单查询用传统RAG，复杂查询用Agentic RAG，可以节省47%成本。

但问题来了：**如何自动判断查询的复杂度？**

这一讲，我们将构建一个**智能路由器**，让系统自动识别查询类型，动态选择最合适的RAG引擎。

---

## 一、为什么需要智能路由器？

### 问题场景

假设我们已经有了传统RAG和Agentic RAG两个引擎，用户提问：

```python
# 问题1
"孙悟空是谁？"  # 应该用哪个引擎？

# 问题2
"分析孙悟空的性格特点和成长历程"  # 应该用哪个引擎？
```

**人类很容易判断**：
- 问题1是简单查询→用传统RAG（快速、经济）
- 问题2是复杂查询→用Agentic RAG（智能、全面）

**但系统如何自动判断？**

这就是智能路由器要解决的问题。

### 路由器的职责

```
┌─────────────────────────────────────────────────┐
│              智能路由器(Router)                    │
│                                                 │
│  输入: 用户查询                                    │
│  输出: 路由决策                                    │
│                                                 │
│  职责:                                           │
│  1️⃣ 分析查询复杂度 (simple vs complex)            │
│  2️⃣ 选择RAG策略 (traditional vs agentic)         │
│  3️⃣ 输出决策理由 (可解释性)                        │
└─────────────────────────────────────────────────┘
```

### 路由器的价值

| 维度 | 无路由器 | 有路由器 |
|------|---------|---------|
| **策略选择** | 固定单一策略 | 动态自适应 |
| **成本** | 全部用Agentic（¥9,000/月） | 混合使用（¥4,800/月） |
| **性能** | 全部慢（8秒）or 全部准确率低（65%） | 平衡（3秒 + 71%准确率） |
| **用户体验** | 简单问题也要等很久 | 快慢结合，体验最优 |

## 二、路由器设计方案

### 设计挑战

1. **准确性挑战**：如何准确识别复杂度？
2. **性能挑战**：路由器本身不能太慢
3. **成本挑战**：路由决策不能增加太多成本

### 两层设计架构

我们采用**快速筛选 + LLM深度分析**的两层架构：

```
用户查询
   ↓
┌────────────────┐
│ 第1层：快速筛选 │  ← 基于关键词规则（0成本，<1ms）
│ (Quick Filter) │
└────┬───────────┘
     │
  明确？
     ├─ 是 → 返回决策
     │
     └─ 否
        ↓
┌────────────────┐
│ 第2层：LLM分析 │  ← 使用LLM深度判断（低成本，~200ms）
│ (LLM Classify) │
└────┬───────────┘
     ↓
  返回决策
```

**为什么这么设计？**

1. **第1层（快速筛选）**：
   - 处理70%的明确case（如"什么是RAG"）
   - 零成本、极速（<1ms）
   - 基于关键词规则

2. **第2层（LLM分析）**：
   - 处理30%的模糊case（如"RAG的应用"）
   - 低成本（单次<¥0.001）
   - 更准确、更智能

## 三、代码实现（分3部分详解）

### 第1部分：路由器初始化与配置

**这部分要做什么？**

建立路由器的基础设施，连接LLM，定义分类关键词。

```python
"""
智能路由器
Intelligent Query Router

根据查询类型自动选择传统RAG或Agentic RAG
"""

from openai import OpenAI
from typing import Literal
import json
import config


class QueryRouter:
    """查询路由器 - 智能选择RAG策略"""

    def __init__(self):
        """初始化路由器"""
        self.client = OpenAI(
            api_key=config.API_KEY,
            base_url=config.BASE_URL
        )
```

**为什么这么写？**

1. **为什么路由器也需要LLM客户端？**
   - 第2层深度分析需要调用LLM
   - 复杂查询无法用简单规则判断
   - LLM可以理解语义和上下文

2. **为什么用config文件？**
   - 集中管理配置，避免硬编码
   - 便于不同环境切换（开发/生产）
   - 关键词列表可以轻松修改

**config.py中的关键配置：**

```python
# 简单查询关键词（触发传统RAG）
SIMPLE_QUERY_KEYWORDS = [
    "是什么", "什么是", "定义", "谁是", "在哪",
    "多少", "哪年", "哪里", "简介"
]

# 复杂查询关键词（触发Agentic RAG）
COMPLEX_QUERY_KEYWORDS = [
    "为什么", "如何", "分析", "比较", "评价",
    "原因", "影响", "关系", "区别", "优缺点"
]
```

**为什么这些关键词？**

- **简单关键词**：5W1H中的事实性问题（What、Who、Where、When、How many）
- **复杂关键词**：需要推理的问题（Why、How、分析类）
- 基于实际业务积累，可持续优化

---

### 第2部分：第1层 - 快速分类

**这部分要做什么？**

基于关键词进行快速判断，处理明确的简单/复杂查询。

```python
    def _quick_classify(self, query: str) -> Literal["simple", "complex", None]:
        """
        基于关键词的快速分类

        Returns:
            "simple" / "complex" / None (不确定)
        """
        query_lower = query.lower()

        # 检查简单查询关键词
        for keyword in config.SIMPLE_QUERY_KEYWORDS:
            if keyword in query_lower:
                return "simple"

        # 检查复杂查询关键词
        for keyword in config.COMPLEX_QUERY_KEYWORDS:
            if keyword in query_lower:
                return "complex"

        # 不确定，需要LLM判断
        return None
```

**为什么这么写？**

1. **为什么先转小写？**
   - 统一大小写，避免遗漏（"什么是" vs "什么是"）
   - 提高匹配准确性

2. **为什么返回None？**
   - 明确区分"能判断"和"不能判断"
   - `None` 表示需要第2层LLM分析
   - 避免错误的快速判断

3. **为什么简单关键词优先？**
   - 简单查询更常见（通常占70%）
   - 优先匹配简单关键词，提升效率

**匹配示例：**

```python
_quick_classify("什么是RAG？")  # → "simple"
_quick_classify("为什么使用RAG？")  # → "complex"
_quick_classify("RAG的应用场景")  # → None (不确定)
```

---

### 第3部分：第2层 - LLM深度分析

**这部分要做什么？**

当关键词规则无法判断时，使用LLM进行深度语义分析。

```python
    def _llm_classify(self, query: str) -> Literal["simple", "complex"]:
        """
        使用LLM深度分析查询类型

        Returns:
            "simple" 或 "complex"
        """
        prompt = f"""你是一个查询分类专家。请分析以下查询的复杂度。

用户查询: {query}

分类标准:

简单查询 (simple):
- 事实性问题（是什么、谁是、在哪里）
- 直接定义查询
- 单一信息点查询
- 可以从知识库直接检索答案

复杂查询 (complex):
- 需要多步推理（为什么、如何）
- 需要分析、比较、评价
- 需要综合多个信息源
- 需要计算或推导
- 需要最新的外部信息

请以JSON格式回复:
{{
    "complexity": "simple" or "complex",
    "reasoning": "你的判断理由"
}}"""

        try:
            response = self.client.chat.completions.create(
                model=config.MODEL_ID,
                messages=[
                    {"role": "system", "content": "你是一个专业的查询分类专家。请始终以JSON格式回复。"},
                    {"role": "user", "content": prompt}
                ],
                temperature=0.1,  # 低温度保证分类稳定
                max_tokens=200
            )

            content = response.choices[0].message.content.strip()

            # 提取JSON
            if "```json" in content:
                content = content.split("```json")[1].split("```")[0].strip()
            elif "```" in content:
                content = content.split("```")[1].split("```")[0].strip()

            result = json.loads(content)
            complexity = result.get("complexity", "complex")
            reasoning = result.get("reasoning", "N/A")

            print(f"   理由: {reasoning}")

            return complexity if complexity in ["simple", "complex"] else "complex"

        except Exception as e:
            print(f"   ⚠️ LLM分类失败: {e}")
            # 默认使用复杂模式（更安全）
            return "complex"
```

**为什么这么写？**

1. **为什么 `temperature=0.1`？**
   - 分类任务需要确定性
   - 同样的查询应该得到一致的判断
   - 低温度避免随机性

2. **为什么 `max_tokens=200`？**
   - 分类回复很短（只需JSON）
   - 限制token节省成本
   - 200已足够完整回复

3. **为什么异常时默认"complex"？**
   - 安全优先原则（Safe by Default）
   - Agentic RAG能处理所有查询（虽然慢）
   - 避免简单RAG处理不了复杂查询

4. **为什么要提取JSON？**
   - LLM有时会回复markdown格式
   - 需要容错处理，提取纯JSON
   - 提高鲁棒性

**Prompt设计要点：**

- ✅ 明确定义"简单"和"复杂"的标准
- ✅ 给出具体判断维度（推理、综合、计算）
- ✅ 要求JSON格式输出（便于解析）
- ✅ 要求提供reasoning（可解释性）

---

### 第4部分：完整路由流程

**这部分要做什么？**

整合两层分类，输出最终的路由决策。

```python
    def classify_query(self, query: str) -> Literal["simple", "complex"]:
        """
        分类查询类型

        Args:
            query: 用户查询

        Returns:
            "simple" 或 "complex"
        """
        print(f"\n🎯 [路由器] 分析查询类型...")

        # 方法1: 基于关键词的快速判断
        quick_decision = self._quick_classify(query)
        if quick_decision:
            print(f"   快速判断: {quick_decision}")
            return quick_decision

        # 方法2: 使用LLM深度分析
        llm_decision = self._llm_classify(query)
        print(f"   LLM判断: {llm_decision}")
        return llm_decision

    def route(self, query: str) -> dict:
        """
        路由决策

        Args:
            query: 用户查询

        Returns:
            路由结果: {
                "strategy": "traditional" or "agentic",
                "complexity": "simple" or "complex",
                "reasoning": str
            }
        """
        complexity = self.classify_query(query)

        if complexity == "simple":
            strategy = "traditional"
            reasoning = "查询相对简单，使用传统RAG可以快速准确地回答"
        else:
            strategy = "agentic"
            reasoning = "查询较复杂，使用Agentic RAG进行深度推理"

        result = {
            "strategy": strategy,
            "complexity": complexity,
            "reasoning": reasoning
        }

        print(f"\n{'='*60}")
        print(f"🎯 [路由决策]")
        print(f"   查询: {query}")
        print(f"   复杂度: {complexity}")
        print(f"   策略: {strategy.upper()} RAG")
        print(f"   理由: {reasoning}")
        print(f"{'='*60}")

        return result
```

**为什么这么写？**

1. **为什么分两个方法？**
   - `classify_query()`：只负责判断复杂度
   - `route()`：负责完整决策（复杂度+策略+理由）
   - 职责分离，便于测试和复用

2. **为什么返回dict而不是字符串？**
   - 包含更多信息（复杂度、策略、理由）
   - 便于日志记录和分析
   - 提供可解释性

3. **为什么要打印详细日志？**
   - 调试时能看到决策过程
   - 生产环境可分析路由准确性
   - 提升系统透明度

**决策映射：**

```python
simple → traditional RAG
complex → agentic RAG
```

def _hybrid_classify(self, query: str):
    """混合判断：关键词 + 长度 + LLM"""

    # 规则1：关键词
    keyword_result = self._quick_classify(query)
    if keyword_result:
        return keyword_result

    # 规则2：查询长度
    if len(query) < 10:  # 短查询通常是简单问题
        return "simple"
    elif len(query) > 50:  # 长查询通常是复杂问题
        return "complex"

    # 规则3：LLM深度分析
    return self._llm_classify(query)

### 优化4：机器学习分类器

```python
# 使用轻量级ML模型替代LLM分类（更快、更便宜）

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.linear_model import LogisticRegression

class MLRouter:
    def __init__(self):
        self.vectorizer = TfidfVectorizer()
        self.classifier = LogisticRegression()

    def train(self, queries, labels):
        """使用历史数据训练分类器"""
        X = self.vectorizer.fit_transform(queries)
        self.classifier.fit(X, labels)

    def classify(self, query):
        """ML分类（<1ms，零成本）"""
        X = self.vectorizer.transform([query])
        return self.classifier.predict(X)[0]
```

**ML分类器的优势：**
- 成本：¥0（无API调用）
- 速度：<1ms（本地推理）
- 准确率：85-90%（需要训练数据）
